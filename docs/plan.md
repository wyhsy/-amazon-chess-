# 项目计划（分工 · 里程碑 · 节奏 · 风险）

> 适用对象：肆如破竹小组全体 4 人。最后更新：2026-09-13。

## 1. 分工与职责边界

4 个模块、4 个人，一对一负责。**文件所有权是硬边界**：只改自己的文件，需要别人改动时开 Issue + @ 对方确认。

| 模块 | 负责人 | 拥有的文件 | 交付物 |
| --- | --- | --- | --- |
| ① 界面设计 | @guoyi1005 | `ui.py`、`assets/` | 棋盘与棋子渲染、选中/落子交互、非法走法提示、胜负提示与动画、AI 思考等待状态 |
| ② 游戏规则 | @xiong681 | `board.py`、`rule.py`、`test/test_rule.py` | 棋盘模型、走法生成、终局与计分、契约测试（**全队地基**） |
| ③ AI 算法 | @wyhsy | `ai_search.py`、`test/test_search.py`、`main.py` | Minimax + Alpha-Beta、时限控制、难度分级、性能优化 |
| ④ 评估策略 | @qiqiyuexi | `ai_eval.py`、`test/test_eval.py`、`docs/` | 估值函数与权重调优、实验对比数据、报告与答辩材料 |

### 关键路径与依赖

```
② 规则（地基，最先冻结接口）
      ├──> ① 界面（依赖 rule 的公开 API 才能联调）
      ├──> ③ AI 搜索（依赖 legal_moves / apply_move / do_move）
      └──> ④ 评估（依赖棋盘特征，但可用 stub 棋盘先开发）
```

- **② 是全队关键路径**：规则一天不冻结，①③④ 就都在等。所以第 1 周资源要优先给规则。
- ③④ 之间是紧耦合的（搜索调用估值），**这两人的接口必须最早对齐**：`evaluate(board, color) -> int` 的语义（正数对谁有利）一旦定错，会连带搜索方向写反。
- ① 可以在规则未完成前先做"假数据界面"：用固定棋盘画图、处理点击，接口一冻结就接线。

## 2. 里程碑（按周推进，实际截止日自行对齐课程时间）

### M1 规则地基（第 1 周）

- [ ] `docs/interface.md` 的 5 个决策点全部拍板，状态改为"已冻结 v1.0"
- [ ] `board.py`：棋盘模型 + 标准开局（含测试）
- [ ] `rule.py`：走法生成、合法性校验、终局判定
- [ ] `test/test_rule.py` 全绿，覆盖：开局走法数、障碍阻挡、马步、箭头不可自射、无路可走判负
- [ ] 控制台能跑一局随机对局（不依赖界面）

**验收人**：规则负责人演示 + 全队跑 `pytest -q` 通过。

### M2 可玩（第 2 周）

- [ ] `ui.py`：10×10 棋盘渲染、选中高亮、两段式操作（移动→射箭）
- [ ] 人人对战完整一局可下完，胜负/和棋有提示
- [ ] 非法操作（点到障碍、路径被挡）有反馈且不崩溃
- [ ] 界面与规则联调通过（至少 3 人各下完一局）

**验收人**：界面负责人演示，AI 负责人用"人机接口"空实现验通路。

### M3 AI 接入（第 3 周）

- [ ] `ai_search.py`：Minimax + Alpha-Beta 可运行
- [ ] `ai_eval.py`：至少 3 个特征 + 零和一致性测试
- [ ] 人机对战可完整一局；单步思考 ≤ 3 秒（超时降级不卡界面）
- [ ] 难度至少 2 档（简单/困难 → 深度或时限不同）

**验收人**：全队各与 AI 对弈一局，记录 AI 单步耗时与是否出现明显低级失误。

### M4 打磨与交付（第 4 周）

- [ ] AI 强度/速度调优（走法排序、迭代加深、置换表任选其一见成效）
- [ ] 难度 3 档、参数可配置、体验细节（提示动画、悔棋可选）
- [ ] 实验数据：不同深度/权重下的强度与耗时对比表
- [ ] 报告定稿 + 答辩演示脚本（含现场演示流程与备份录屏）
- [ ] README 更新为最终版（含截图/GIF）

**验收人**：组长组织一次完整彩排。

## 3. 每周协作节奏

| 时间 | 活动 | 时长 | 产出 |
| --- | --- | --- | --- |
| 周一 | 站会：过看板、定本周 Issue、认领负责人 | 15 分钟 | 每个人的 Issue 列表 |
| 每日（异步） | 群里发三行：昨日完成 / 今日计划 / 当前阻塞 | — | 早发现卡点 |
| 周四 | **集成日**：把各自的 PR 合进 `dev`，跑冒烟测试 | 30 分钟 | 一个可运行的 `dev` |
| 周日 | 里程碑检查：对照 M1~M4 验收标准打勾 | 20 分钟 | 进度记录（`docs/meeting/`） |

**集成日铁律**：只做合并与修复，不写新功能。避免"周五晚上合并一堆半成品"。

## 4. Issue 与看板使用规范

仓库已开启 Issues 和 Projects，建议：

- **标签**：
  - 模块：`module:rule`、`module:ui`、`module:ai`、`module:eval`、`module:docs`
  - 类型：`type:feature`、`type:bug`、`type:test`、`type:task`
  - 里程碑：`M1`~`M4`（或用 Milestone 功能）
- **粒度**：一个 Issue 0.5~1 天能做完。写"做 AI"太大，写"实现 Alpha-Beta 剪枝并测通简单局面"才合格。
- **模板**：用 `.github/ISSUE_TEMPLATE/task.md`，必须填"依赖"字段——棋类项目最常卡在"接口没好，我只能等"。
- **WIP 限制**：每人同时进行中的 Issue 不超过 1 个（`in progress` 列超过 N 张卡说明并行度失控）。
- 看板列：`Backlog → 本周 → In progress → In review(PR) → Done`

## 5. 风险清单与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | 接口未冻结就并行开发，函数签名对不上 | 大面积返工 | 第 1 周只做接口 + 契约测试；`docs/interface.md` 冻结后再并行 |
| R2 | Python 下搜索太慢，AI"很笨还卡" | 演示翻车 | 第 1 周先测性能基线；优先做走法排序 + 就地回溯；用时限控制保底 |
| R3 | UI 与规则耦合（UI 组去改 rule.py） | 冲突频发 | 依赖方向写进 `docs/interface.md`，CODEOWNERS + Review 把关 |
| R4 | 队友 Git 不熟（push 被拒、冲突不会解） | 卡进度、可能推错分支 | 第 1 周结对演示一次完整 PR 流程；`docs/setup.md` 速查；红线写清 |
| R5 | 网络不稳，推送反复失败 | 反复消耗时间 | 配代理或 SSH（见 CONTRIBUTING 第 7 节）；**不要**搞 Gitee 双远端 |
| R6 | 中文文件名/路径导致编码问题 | 报错难排查 | 分支名、变量名、文件名全英文；文本文件统一 UTF-8 |
| R7 | 期末和其它课程撞车，集中在最后一周赶工 | 质量崩盘 | 报告素材随手记进 `docs/`；M4 留出至少 3 天缓冲 |
| R8 | 只有 1 人干活（贡献不均） | 分数与信任受损 | 看板 + PR 记录天然留痕；任务按人认领，周会核对 |

## 6. 报告与答辩分工

| 章节 | 主笔 | 说明 |
| --- | --- | --- |
| 需求分析与规则形式化 | 规则负责人 | 把棋盘/走法/终局写成形式化描述 |
| 系统设计 | 界面负责人 | 模块图、依赖方向、UI 交互流程（配截图） |
| 算法设计与实现 | AI 负责人 | Minimax、Alpha-Beta 伪代码与剪枝分析、复杂度 |
| 评估函数与实验 | 评估负责人 | 特征设计、权重、对比实验表（深度 vs 耗时 vs 胜率） |
| 测试与总结 | 全队 | 测试用例统计、问题与改进、个人分工说明 |
| 答辩演示 | 全队，组长串场 | 按 M1→M4 讲故事，现场跑一局困难档 |

## 7. 会议记录
