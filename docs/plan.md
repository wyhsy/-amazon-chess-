# 项目计划（分工 · 里程碑 · 节奏 · 风险）

> 适用对象：肆如破竹小组全体 4 人。最后更新：2026-09-13。

## 1. 分工与职责边界

4 个模块、4 个人，一对一负责。**文件所有权是硬边界**：只改自己的文件。

工作方式：**组长定接口与任务 → 队友在各自模块内实现 → 组长审阅并合并 PR**。队友不需要参与仓库设置，也不需要 Approve 任何 PR。

| 模块 | 负责人 | 拥有的文件 | 交付物 |
| --- | --- | --- | --- |
| ① 界面设计 | @guoyi1005 | `ui.py`、`assets/` | 棋盘与棋子渲染、选中/落子交互、非法走法提示、胜负提示与动画、AI 思考等待状态 |
| ② 游戏规则 | @xiong681 | `board.py`、`rule.py`、`test/test_rule.py` | 棋盘模型、走法生成、终局与计分、契约测试（**全队地基**） |
| ③ AI 算法 | @wyhsy | `ai_search.py`、`test/test_search.py`、`main.py` | Minimax + Alpha-Beta、时限控制、难度分级、性能优化 |
| ④ 评估策略 | @qiqiyuexi | `ai_eval.py`、`test/test_eval.py`、`docs/` | 估值函数与权重调优、实验对比数据、报告与答辩材料 |

### 关键路径与依赖

```
② 规则（地基，最先冻结接口）
      ├──> ① 界面（依赖 rule 的公开 API 才能联调）
      ├──> ③ AI 搜索（依赖 legal_moves / apply_move / do_move）
      └──> ④ 评估（依赖棋盘特征，但可用 stub 棋盘先开发）
```

- **② 是全队关键路径**：规则一天不冻结，①③④ 就都在等。所以第 1 周资源要优先给规则。
- ③④ 之间是紧耦合的（搜索调用估值），**这两人的接口必须最早对齐**：`evaluate(board, color) -> int` 的语义（正数对谁有利）一旦定错，会连带搜索方向写反。
- ① 可以在规则未完成前先做"假数据界面"：用固定棋盘画图、处理点击，接口一冻结就接线。

### M4 打磨与交付（第 4 周）

- [ ] README 更新为最终版（含截图/GIF）

**验收人**：组长组织一次完整彩排。

## 3. 推进节奏（组长派任务 + 异步汇报）

| 时间 | 做什么 | 谁 |
| --- | --- | --- |
| 每周一 | 组长把本周任务写成 Issue（模块 + 验收标准 + 参考 `docs/tasks/`），在群里派发 | 组长 |
| 每天（异步） | 队友在群里发三行：昨天做完什么 / 今天做什么 / 卡在哪 | 队友 |
| 随时 | 队友提 PR → 组长审阅（看模块边界 + CI 是否绿）→ Squash and merge | 组长 |
| 每周日 | 组长对照 M1~M4 打勾，更新 `README.md` 进度与 `docs/meeting/` 记录 | 组长 |

**组长审 PR 只看三件事**：① 有没有动别人模块的文件 ② CI 是否全绿 ③ 是否符合 `docs/interface.md`。其余细节不必纠结，能跑、能测就行。

## 4. 任务派发（Issue）

- 组长用 `.github/ISSUE_TEMPLATE/task.md` 建 Issue 派活，**每个 Issue 0.5~1 天能做完**。反面例子："做 AI"；正面例子："实现 Alpha-Beta 剪枝并测通简单局面"。
- Issue 必须写清：**文件清单**（只改这些）、**依赖**（需要谁先完成）、**验收标准**（怎么算做完）。
- 队友认领后拖到 `In progress`；提了 PR 拖到 `In review`；组长合并后拖到 `Done`。
- 标签按需建：`module:rule` / `module:ui` / `module:ai` / `module:eval` / `module:docs`、`type:feature` / `type:bug` / `type:test`。

| R5 | 网络不稳，推送反复失败 | 反复消耗时间 | 配代理或 SSH（见 CONTRIBUTING 第 7 节）；**不要**搞 Gitee 双远端 |

| R7 | 期末和其它课程撞车，集中在最后一周赶工 | 质量崩盘 | 报告素材随手记进 `docs/`；M4 留出至少 3 天缓冲 |
